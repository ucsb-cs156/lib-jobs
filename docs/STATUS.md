## Library release status

- **v0.3.3** (fixes a job-chaining transaction-visibility race in
  `JobService.runAsJob` — the initial `queued` row's save now runs in its
  own `REQUIRES_NEW` transaction, same idiom already used for log writes
  and cancellation re-fetches) is the current released version, tagged
  2026-08-25 and verified resolvable on JitPack. Surfaced proactively by a
  session working on citelines issue #110 (job chaining is part 2 of that
  work, not yet built) before any app hit it live — full analysis at
  `docs/job-chaining-analysis.md`, resolved version in `DESIGN.md` §10.
  Not hypothetical: courses already runs `jobsExecutor` at pool-size 2, so
  it was one un-reviewed chaining call site away from hitting this for
  real. Empirically verified with a hand-verified red/green integration
  test (fails with a clean 10-second timeout when reverted). **Scaffold,
  courses, dining, and frontiers are fully adopted on v0.3.2** (PR #121,
  PR #331, PR #147, and PR #700 respectively, all merged and verified);
  none of them chain jobs today, so v0.3.2 remains correct for them —
  **citelines is bumping straight to v0.3.3** (PR #125, open) since it's
  the one about to build chaining.
- **v0.3.2** (`JobContext.checkCancellation()` made public — same
  re-fetch-and-throw behavior as the check already inside `log()`, but
  callable directly with no log line written) — superseded by v0.3.3 for
  any app that chains jobs or might soon; still correct and current for
  every app that doesn't. Built 2026-08-21, the same day as v0.3.1, after
  live QA testing of v0.3.1's own timeout fix on scaffold surfaced a third
  issue: a job body with a loop that only logs on specific branches (the
  common case being silent) never gave cancellation a checkpoint to fire
  from during that silence — see `CLAUDE.md`'s v0.3.2 entry for the full
  incident.
- **v0.3.1** (startup recovery sweep — `@EventListener(ApplicationReadyEvent.class)`
  on `JobService` marks any job still `queued`/`running`/`cancelling` at
  boot as a new terminal status, `interrupted`; zero app wiring required)
  — superseded by v0.3.2 the same day.
- **v0.3.0** (job cancellation — `POST /api/jobs/{id}/cancel`, cooperative
  cancellation checked on every `ctx.log()` call, `docs/DESIGN.md` §9) —
  superseded by v0.3.2/v0.3.3; no app should adopt v0.3.0 or v0.3.1 alone.
- **v0.2.0** (job-log storage redesign — normalized `job_logs` table,
  `/paginated` filtering, incremental log tailing) — superseded by v0.3.x
  but still what happycows currently runs.

**Rollout order for v0.3.x adoption** (Phill, 2026-08-21): citelines →
scaffold → frontiers → dining → courses. happycows excluded — frozen until
~2026-09-15 (see the table above). **Order adjusted twice since:** citelines
was mid-deploy, so scaffold went first (2026-08-21, done); then citelines
had unrelated cleanup work in progress, so courses went next (2026-08-22,
done 2026-08-24); dining picked up next and finished 2026-08-24 (PR #147);
frontiers picked up next and finished 2026-08-25 (PR #700, citelines
still had unrelated cleanup in progress); citelines picked up last,
PR #125 open 2026-08-25. **The v0.3.x rollout is now effectively complete
for every app except happycows** (frozen until ~2026-09-15) — all five
other apps have a v0.3.x bump merged or open.

**Standing action items for every v0.3.x rollout PR** (Phill, 2026-08-21),
both found during scaffold's live QA testing and unrelated to lib-jobs
itself, but newly consequential now that jobs run on a single-threaded
executor by default:
1. Audit that app's own blocking HTTP calls (RestTemplate, HttpClient,
   etc.) for missing timeouts — an untimed call can wedge the entire
   queue forever, and only a genuine restart (not cancellation) recovers
   it.
2. Check that app's own job bodies for a loop that only calls
   `ctx.log(...)` on specific branches (e.g. a "skip"/"error" case, with
   the common case being silent) — such a loop never gives cancellation a
   checkpoint to fire from during its silent stretches. Add
   `ctx.checkCancellation()` (v0.3.2+) once per iteration where found.

Scaffold hit both for real on QA and fixed them in #121 alongside its
v0.3.0→v0.3.2 bump; courses, frontiers, and citelines each hit both
proactively (fixed before any live bug report) in #331, #700, and #125
respectively — frontiers the largest instance of item 2 (6 job classes,
10 total checkpoints); citelines' item 1 needed a mid-course correction
after the first RestTemplate timeout attempt broke every `@WebMvcTest`
slice (see its STATUS.md row above).

## Keeping this up to date

Re-run the check above after any app-repo PR that bumps (or newly adds) the
`lib-jobs` dependency:

```bash
for repo in proj-citelines proj-courses proj-dining proj-frontiers proj-happycows proj-scaffold; do
  echo "=== $repo ==="
  gh api "repos/ucsb-cs156/$repo/contents/pom.xml?ref=main" --jq '.content' 2>/dev/null \
    | base64 -d 2>/dev/null | grep -A2 "artifactId>lib-jobs<"
done
```
